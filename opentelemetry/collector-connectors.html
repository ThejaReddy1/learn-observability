Collector Connectors:
Joining Pipelines Together

A Connector is the one component type that sits between two pipelines — acting as an exporter on one and a receiver on the other. This guide covers every connector type: Count, SpanMetrics, ServiceGraph, Routing, Forward, Sum, and Exceptions — with full YAML examples for each.

Thejasekhar Reddy.G  ·  June 14, 2026

01 — What Is a ConnectorBoth an Exporter and a Receiver at Once

Connectors help in joining two pipelines — making telemetry from one pipeline act as a source, and a second pipeline receives data from it. That's the whole idea. One pipeline finishes, and instead of sending data to an external backend, it hands off to another pipeline inside the same Collector process.

Connector — acts as both Exporter on one pipeline and Receiver on the next

A Connector acts as an exporter on the first pipeline and a receiver on the second pipeline. This allows the Collector to hand off data, enables pipeline chaining, and makes cross-signal flows possible — like turning trace data into metrics, or extracting exceptions from spans into logs.

Why this matters

Before Connectors, if you wanted to derive metrics from traces you needed a separate tool. Now it happens inside the Collector itself. No extra infrastructure, no extra hops. The trace pipeline and the metrics pipeline are wired together by a single component.

02 — Count ConnectorAny Signal → Metrics

The Count Connector counts spans, metrics, or logs and converts them into timeseries metrics. You define which events to count and under what conditions. It's the simplest way to produce a counter metric from any telemetry signal flowing through your Collector.

Count Connector — counting prod span events into a metric
connectors:
  count:
    spanevents:
      my.prod.event.count:
        description: Number of span events tagged as Prod
        conditions:
          - 'attributes["env"] == "Prod"'
          - 'name == "prodevent"'

service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [count]   # count acts as exporter here
    metrics:
      receivers: [count]   # count acts as receiver here
      exporters: [otlp]
How the service wiring works

count appears twice — as exporter and as receiver

In the traces pipeline, count is listed under exporters — spans flow into it. In the metrics pipeline, count is listed under receivers — metrics flow out of it. The same component name, two roles. That's the Connector pattern.

03 — SpanMetrics ConnectorTraces → Metrics · RED for Free

The SpanMetrics Connector generates metrics directly out of your existing spans. No additional instrumentation needed. It produces Rate, Error rate, and Duration (RED) metrics automatically — the three signals every SRE wants for every service.

What it produces

traces.span.metrics.calls_total — request rate by service, operation, status. traces.span.metrics.duration — latency histogram with configurable buckets. Both tagged with whatever dimensions you configure.

Why it's powerful

You already pay the cost of tracing. SpanMetrics lets you extract service-level metrics from those traces for free — no application changes, no separate metric instrumentation. One pipeline feeds two observability pillars.

SpanMetrics Connector — RED metrics from traces, no extra instrumentation
connectors:
  spanmetrics:
    histogram:
      explicit:
        buckets: [100us, 1ms, 2ms, 6ms, 10ms, 100ms, 250ms]
    dimensions:
      - name: http.method
      - name: http.status_code

service:
  pipelines:
    traces:
      receivers:  [otlp]
      exporters:  [spanmetrics]   # spans exit here
    metrics:
      receivers:  [spanmetrics]   # RED metrics enter here
      exporters:  [otlp]

04 — ServiceGraph ConnectorTraces → Service Dependency Map

The ServiceGraph Connector maps service dependencies in real time for traces. It observes client and server spans, detects which services call which, and produces metrics that represent the edges of your service graph. Feed those metrics into Grafana and you get a live dependency map without any manual configuration.

🗺️
What it builds
It reads the span kind (CLIENT/SERVER) and the service.name resource attribute to build edges between services. Every unique caller-callee pair becomes a metric with rate, error, and duration dimensions.
📊
Signal direction
Traces in → Metrics out. Same pipeline wiring as SpanMetrics. Use both together if you want RED metrics and a dependency map from the same trace pipeline.
service_graph connector — traces in, service topology metrics out
# Note: renamed from servicegraph to service_graph (snake_case)
# The old name still works but is deprecated

connectors:
  service_graph:
    # how long to cache spans waiting for their client/server pair to arrive
    store:
      ttl:        2s
      max_items:  1000
    latency_histogram_buckets:
      [2ms, 5ms, 10ms, 25ms, 50ms, 100ms, 250ms, 500ms, 1s, 2.5s]
    # extra dimensions to add to each graph edge metric
    dimensions:
      - service.namespace
      - deployment.environment

service:
  pipelines:
    traces:
      receivers:   [otlp]
      processors:  [batch]
      exporters:   [service_graph, otlp]   # fan-out: traces go to backend AND graph connector
    metrics/servicegraph:
      receivers:   [service_graph]   # edge metrics arrive here
      processors:  [batch]
      exporters:   [prometheus/servicegraph]
What metrics it produces

One metric per service-to-service edge

For every unique caller-callee pair the connector produces traces_service_graph_request_total (request rate), traces_service_graph_request_failed_total (error rate), and traces_service_graph_request_duration_seconds (latency histogram). Each metric carries client and server labels identifying the edge. Feed these into Grafana's Node Graph panel and your service map builds itself.

05 — Routing ConnectorOne Pipeline In, Many Pipelines Out

The Routing Connector routes telemetry to specific pipelines based on OTTL rules — evaluated against attributes or resource attributes. The most common use case is multi-tenant routing: based on tenant data, route data to different pipelines and different backends.

Routing Connector — OTTL rules decide which pipeline receives the data
default_pipelines

Always set default_pipelines. If an incoming record matches none of your routing rules, it goes there. Without a default, unmatched data is silently dropped.

routing connector — route logs by deployment.environment to different backends
connectors:
  routing/env:
    error_mode:        ignore
    default_pipelines: [logs/default]   # no match → goes here
    table:
      # context defaults to resource — evaluated against resource.attributes
      - context:    resource
        statement:  route() where attributes["deployment.environment"] == "production"
        pipelines:  [logs/prod]
      - context:    resource
        statement:  route() where attributes["deployment.environment"] == "staging"
        pipelines:  [logs/dev]

service:
  pipelines:
    # Entry pipeline — all logs arrive here first
    logs:
      receivers:   [filelog]
      exporters:   [routing/env]   # connector acts as exporter here

    # Downstream pipelines — connector acts as receiver for each
    logs/prod:
      receivers:   [routing/env]
      processors:  [batch]
      exporters:   [otlp/prod]

    logs/dev:
      receivers:   [routing/env]
      processors:  [batch]
      exporters:   [otlp/dev]

    logs/default:
      receivers:   [routing/env]
      processors:  [batch]
      exporters:   [otlp/dev]   # unmatched records fall back here

statement vs condition

Use statement with route() where ... for most cases. Use condition (a plain boolean OTTL expression) when routing by request context. Both work — statement is the more common form from the official README.

action: copy vs move

Default action is move — matched data goes to the target pipeline only. Set action: copy to send the same record to multiple pipelines while still evaluating subsequent routing rules. Useful for fan-out scenarios.

06 — Other ConnectorsForward, Sum, and Exceptions

Any → Any

Forward Connector

It simply forwards data from one pipeline to the next unchanged. Useful when you want to fan-in multiple pipelines into one without any transformation.

Any → Metrics

Sum Connector

Converts numeric attributes on spans or logs into time-series metrics. If a span carries a field like http.response_size, Sum can accumulate those values into a running metric.

Traces → Logs

Exceptions Connector

Extracts exception events from spans and converts them into log records. Perfect for error-related pipelines that need trace details included in the logs.

Exceptions Connector — extract exception events from spans into logs
connectors:
  exceptions:   # no config needed — extracts all exception events

service:
  pipelines:
    traces:
      receivers:  [otlp]
      exporters:  [otlp, exceptions]  # fan-out: traces go to backend AND exceptions
    logs:
      receivers:  [exceptions]       # exception events arrive as logs here
      exporters:  [otlp]

07 — SummaryConnector Signal Matrix

Here's the full picture of what each Connector does and which signals it converts between. Pick the right one based on what signal you have and what you need to produce.

Cross-signal Connectors

SpanMetrics — Traces → Metrics (RED)
ServiceGraph — Traces → Metrics (topology)
Count — Any → Metrics (counters)
Sum — Any → Metrics (numeric attrs)
Exceptions — Traces → Logs

Routing + Utility Connectors

Routing — Any → Any (OTTL-based fan-out)
Forward — Any → Any (passthrough fan-in)

All Connectors appear under connectors: in your config and must be listed in both an exporter and a receiver role inside service.pipelines.

"A Connector acts as an exporter on the first pipeline and a receiver on the second. That's it. Everything else is just what it does with the data in between."
