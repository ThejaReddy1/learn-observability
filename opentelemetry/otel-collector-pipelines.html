Building Telemetry Pipelines

A complete guide to processors, transformations, connectors, distributions, debugging, and production deployment patterns — with real config examples throughout.

01 — FoundationsThe Collector Is Defined by YAML

The Collector's behavior is entirely defined by a YAML configuration file. For any pipeline setup, you need to understand three top-level sections: receivers, exporters, and service.

📥
Receivers
The entry points of all telemetry data coming into the Collector from your application and infrastructure. They listen for incoming data and hand it off to the pipeline.
📤
Exporters
The final destination for all telemetry data leaving the Collector after it has been processed. You can have multiple exporters sending the same data to different backends simultaneously.
🎛️
Service
The central orchestrator that activates and defines the flow of data through the Collector. No component is active unless it is enabled here. It works by defining pipelines for each signal type (traces, metrics, logs), and each pipeline specifies the exact path data will take by linking receivers, processors, and exporters.
Pipeline: Receiver → [Processors] → Exporter

The Simplest Possible Pipeline

Before adding any processors, start here. This is the minimum config that proves data is flowing — an OTLP receiver accepting logs over gRPC on port 4317, a debug exporter printing everything to the console, and a service block wiring them together.

otelcol.yaml — the simplest possible pipeline
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

exporters:
  debug:
    verbosity: detailed   # prints full content to stderr — dev only

service:
  pipelines:
    logs:
      receivers:  [otlp]
      exporters:  [debug]

Run the Collector and a synthetic data generator using Docker Compose to verify data is flowing before adding any complexity.

docker-compose.yml — Collector + synthetic log generator
services:
  otelcol:
    image: otel/opentelemetry-collector-contrib:0.153.0
    container_name: otelcol
    volumes:
      - ./otelcol.yaml:/etc/otelcol-contrib/config.yaml
    restart: unless-stopped

  otelgen:
    image: ghcr.io/krzko/otelgen:v0.5.2
    container_name: otelgen
    command:
      - "--otel-exporter-otlp-endpoint"
      - "otelcol:4317"
      - "--insecure"
      - "logs"
      - "multi"
    depends_on:
      - otelcol

networks:
  otelnet:
    driver: bridge
Start and watch
# Start both services
docker compose up -d

# Watch the Collector output — you should see logs flowing immediately
docker compose logs otelcol -f --no-log-prefix

02 — Understanding the DataTelemetry Records: Logs Deep Dive

Before you can transform telemetry, you need to understand its structure. Let's walk through what a log record actually looks like inside the Collector.

ResourceLogs and Resource Attributes

📦
ResourceLog #0 — The top-level container
The #0 indicates it's the first resource log in this batch. All telemetry within this block comes from the same Resource — a service, container, or host machine.
🏷️
ResourceAttributes — Key-value pairs describing the entity
These describe the entity that produced the logs — a service, container, or host machine. Example attributes: service.name, k8s.pod.name. These are applied to every log generated by this resource.

ScopeLogs

🔭
ScopeLogs #0 — Grouped by instrumentation scope
Within a resource, telemetry is grouped by its origin, known as the instrumentation scope. This block contains all logs from a single scope.
📍
Instrumentation Scope
Identifies the specific library or module that generated the log. This is useful for knowing which part of your application emitted the log.

LogRecord — The actual log entry

Within a single ResourceLog block, you may see multiple LogRecord entries — they all belong to the same parent Resource. Key fields on each LogRecord:

⏱️
Timestamp
When the event occurred.
🔢
SeverityNumber / SeverityText
The log level — such as ERROR or INFO. SeverityNumber is the numeric representation (e.g. INFO = 9).
💬
Body
The actual log message content.
📋
Attributes
Contextual field pairs that provide context specific to that log event. You'll see the explicit data type for each value, which is very helpful when manipulating telemetry data with OTTL.
🔗
TraceId / SpanId
These top-level fields are crucial for correlation. When populated, they directly link a log to a specific trace and span, allowing you to navigate between logs and traces in your observability backend.

What a Real Log Record Looks Like

Here is what the debug exporter actually prints when a log record flows through your pipeline. This is the raw, unprocessed output — exactly what arrives at the Collector before any processors touch it.

        -> trace_flags:       Str(01)                                 # ⚠ wrong place

        -> k8s.pod.name:      Str(checkout-pod-ab06ca8b)             # ⚠ duplicate
        -> http.method:       Str(POST)                               # ⚠ deprecated
        -> http.status_code:  Int(500)                               # ⚠ deprecated

      Trace ID:   (empty)
      Span ID:    (empty)

There are three issues in this record that the transform processor fixes. Misplaced trace context — trace_id, span_id, and trace_flags are sitting inside the Attributes map when they belong in the dedicated top-level fields. Backends rely on those top-level fields for log-to-trace correlation. Redundant attributes — service.name and k8s.pod.name already live on the Resource, so carrying them again on every LogRecord wastes storage. Deprecated HTTP attributes — http.method and http.status_code are deprecated in favour of http.request.method and http.response.status_code.

After the transform processor runs — moving trace context to the right fields, deleting the duplicates, and renaming the HTTP attributes — the same record looks like this:

Clean log record — after transform processor, correct and compact
ResourceLog #0
  Resource attributes:
    -> host.name:           Str(node-1)
    -> k8s.container.name: Str(checkout-service)
    -> k8s.namespace.name: Str(default)
    -> k8s.pod.name:       Str(checkout-pod-ab06ca8b)
    -> service.name:       Str(checkout-service)

  ScopeLogs #0
    InstrumentationScope checkout-service

    LogRecord #0
      Timestamp:         2025-07-06 11:21:57.085420886 +0000 UTC
      SeverityText:      Error
      SeverityNumber:    Error(17)
      Body:              Str(order payment failed for user 1234)
      Attributes:
        -> worker_id:                  Str(1234)
        -> phase:                      Str(checkout)
        -> http.request.method:        Str(POST)      # ✓ updated
        -> http.response.status_code:  Int(500)       # ✓ updated
      Trace ID:  46287c1c7b7eebea22af2b48b97f4a49    # ✓ now in correct field
      Span ID:   f5777521efe11f94                    # ✓ now in correct field
      Flags: 1                                       # ✓ now in correct field
Why this matters in practice

The before/after difference isn't cosmetic. The clean record is smaller — no redundant fields. Log-to-trace correlation works — backends use the top-level Trace ID and Span ID fields, not attributes. And your queries are consistent — http.request.method is the current semantic convention that every downstream tool understands.

03 — ProcessingProcessing and Transforming Telemetry

The real power of the Collector lies in its ability to process data in-flight. This is where processors come in. Processors are intermediary components in a pipeline that can inspect, modify, filter, and enrich your telemetry.

Receiver → [Processors] → Exporter

Batching Telemetry for Efficiency

Sending every single span or metric individually over the network is incredibly inefficient. It creates high network traffic and puts unnecessary load on your backends. The batch processor solves this by grouping telemetry into batches before exporting.

batch processor — add to processors: section and wire into service.pipelines
processors:
  batch:
    # send when either condition is met first
    send_batch_size: 8192    # send when batch reaches this many items
    timeout:         200ms    # or when this time elapses — whichever comes first

service:
  pipelines:
    logs:
      receivers:   [otlp]
      processors:  [batch]   # add to processors list — order matters
      exporters:   [otlphttp]

With this config, your Collector buffers data for up to 200ms or until 8192 items accumulate, then sends it to the exporters in one efficient action.

Reducing Noise by Filtering Telemetry

Observability data can be noisy. Frequent DEBUG level logs are often useful in development but can be costly and redundant in production. Use the filter processor, which lets you drop telemetry data using the powerful OpenTelemetry Transformation Language (OTTL).

filter processor — drop noisy logs, keep only INFO and above
processors:
  filter:
    error_mode: ignore
    logs:
      log_record:
        # DROP any log below INFO — TRACE and DEBUG are discarded
        - severity_number < SEVERITY_NUMBER_INFO

service:
  pipelines:
    logs:
      receivers:   [otlp]
      processors:  [filter, batch]   # filter first, then batch
      exporters:   [otlphttp]

Now any log with a severity number less than 9 (INFO) will be dropped before reaching the exporter.

Modifying and Enriching Telemetry Data

When you need to add, remove, or modify attributes in your telemetry data, there are three general-purpose processors:

🏗️
resourceprocessor
For actions targeting resource-level attributes — e.g. host.name, service.name. Operates on the Resource object that wraps your telemetry.
🔧
attributeprocessor
For simple actions on the attributes of individual logs, spans, or metrics. Good for inserting, updating, deleting, or hashing specific attribute values.
⚡
transformprocessor
The most powerful of the three — for performing complex transformations on any part of your telemetry data using OTTL statements.

Use cases for these processors: redacting or removing sensitive information before it leaves your systems; enriching data by adding static attributes; renaming or standardizing attributes to conform to semantic conventions across different services; correcting malformed or misplaced data sent by older or misconfigured instrumentation.

Real OTTL Transformations

Here are three common real-world transformations using the transformprocessor:

1. Misplaced Trace Context

Moving trace data out of Attributes (wrong place) up to the top-level fields (correct place) where the Collector and backends expect them.

2. Redundant Attributes

Resource attributes like k8s.pod.name and service.name are deduplicating in the log record's attributes — delete them from the lower level.

3. Deprecated Attributes

HTTP attributes like http.method, http.target, and http.status_code have been deprecated in favor of newer semantic conventions.

OTTL Functions

set(field, value) — sets a value. delete_key(attributes, "key") — removes the original key. Statements run in order within each context block.

transform processor — fix trace context, remove duplicates, rename deprecated HTTP attrs
processors:
  transform:
    error_mode: ignore
    log_statements:
      # 1. Move trace context from attributes to the correct top-level fields
      #    Backends use these top-level fields for log-to-trace correlation
      - context: log
        statements:
          - set(trace_id.string, attributes["trace_id"])
          - set(span_id.string, attributes["span_id"])
          - set(flags, Int(attributes["trace_flags"]))

      # 2. Delete the now-redundant trace context attributes
      - context: log
        statements:
          - delete_key(attributes, "trace_id")
          - delete_key(attributes, "span_id")
          - delete_key(attributes, "trace_flags")

      # 3. Delete attributes already present on the Resource — no need to repeat them
      - context: log
        statements:
          - delete_key(attributes, "service.name")
          - delete_key(attributes, "k8s.pod.name")
          - delete_key(attributes, "k8s.namespace.name")
          - delete_key(attributes, "k8s.container.name")

      # 4. Rename deprecated HTTP attributes to current semantic conventions
      - context: log
        statements:
          - set(attributes["http.request.method"], attributes["http.method"])
          - delete_key(attributes, "http.method")
          - set(attributes["http.response.status_code"], attributes["http.status_code"])
          - delete_key(attributes, "http.status_code")

service:
  pipelines:
    logs:
      receivers:   [otlp]
      processors:  [filter, transform, batch]
      exporters:   [otlphttp]

04 — ResilienceEnsuring Resilience with Memory Limiter

An overloaded service could suddenly send a massive flood of data, overwhelming the Collector and causing it to run out of memory and crash. This would create a total visibility outage.

The memory_limiter processor acts as a safety valve to prevent this. It monitors memory usage and starts rejecting data if it exceeds a configured limit, enforcing backpressure on the data source.

memory_limiter:
  check_interval: 1s
  limit_mib: 400
  spike_limit_mib: 100
⚠️ Critical Rule

The memory_limiter must come first in your pipeline's processor list. If it's over the limit, you want to reject data immediately — before wasting CPU cycles on other processing.

05 — Advanced PipelinesHandling Multiple Signal Types with Parallel Pipelines

You can handle traces, metrics, and logs simultaneously by defining parallel pipelines — one for each signal type — in the service section. Each runs independently with its own receiver, processor, and exporter chain.

Fanning Out to Multiple Destinations

A key advantage of the OTel Collector is its ability to easily route telemetry to multiple destinations at once — a concept called "fanning out". This is simply done by adding more exporters to a pipeline's exporters list. The same data flows to all of them simultaneously.

06 — ConnectorsChaining Pipelines with Connectors

You can create powerful data processing flows by generating new telemetry signals from your existing data. This is possible with connectors. A connector is a special component that acts as both an exporter for one pipeline and a receiver for another — allowing you to chain pipelines together.

Example: counting the number of errors by creating a metric named log-error.count that increments every time it sees a log with a severity of ERROR or above — using the count connector.

Connectors — Chaining Pipelines Together
connectors:
  count/log-errors:
    logs:
      log-error.count:
        description: count of errors logged
        conditions:
          - severity_number >= SEVERITY_NUMBER_ERROR

service:
  pipelines:
    logs:
      receivers: [...]
      processors: [...]
      exporters: [debug, count/log-errors]
    metrics:
      receivers: [count/log-errors]
      processors: [memory_limiter, batch]
      exporters: [debug]

It allows you to derive new insights from existing data streams directly within the Collector. Another powerful connector is the spanmetric connector — it automatically generates RED metrics (request rates, error counts, and duration histograms) directly from your trace data. Note: at this time it is in alpha state.

07 — DistributionsCollector Distributions

When you use the OpenTelemetry Collector, you are not running a single monolithic application. Instead you use a distribution — a specific binary packaged with a curated set of components (receivers, processors, exporters, and extensions). There are three types:

01 — Official OpenTelemetry Distributions

Core & Contrib

Core (otelcol): Minimal, lightweight distribution that includes only the most essential and stable components. Contrib (otelcol-contrib): The most comprehensive version — includes almost every component from both core and contrib repositories. Recommended for getting started.

02 — Vendor Distributions

Pre-configured for specific backends

Typically based on otelcol-contrib but pre-configured with the vendor's specific exporter and other recommended settings. Good if you're committed to a specific backend.

03 — Custom Distributions

Recommended for production

For production environments, the recommended practice is to build your own custom distribution using the OpenTelemetry Collector Builder (ocb) tool. Create a simple manifest file listing the components you want, then run the ocb tool to compile your custom binary — minimal attack surface, exactly what you need.

08 — DebuggingDebugging and Observing Your Pipeline

Validating Your Configuration

$ otelcol-contrib validate --config=config.yaml

Live Debugging with zPages

For debugging the Collector components themselves, you can enable the zPages extension. Once the Collector is running, you can access several debugging pages:

/debug/pipelinez

View your pipeline components, their configuration, and data flow statistics in real time.

/debug/tracez

See recently sampled traces passing through the Collector — useful for verifying trace data is flowing correctly.

extensions:
  zpages:
    # default endpoint is localhost:55679

service:
  extensions: [zpages]

Observing the Collector's Internal Telemetry

In production environments you'll need to monitor the Collector's health and performance over time. This is configured under the service.telemetry section. By default, the Collector sends its own internal logs to stderr — it's often the first place you'll check when there's a problem with your pipeline.

Key metrics to watch

Scrape localhost:8888/metrics and watch: otelcol_processor_dropped_metric_points and otelcol_exporter_send_failed_metric_points — these are the canaries that tell you your pipeline is struggling before users notice.

09 — ProductionGoing to Production: Collector Deployment Patterns

Production Deployment Patterns
Pattern 01

Agent-only Deployment

Simplest setup. One Collector per host, co-located with your application. Good for small environments or when getting started.

Application → OTel Collector (Agent) → O11y Backend
Pattern 02

Agent and Gateway Deployment

Agent collectors handle metadata enrichment efficiently at the edge. The gateway provides centralized control, security, and heavy processing. Best of both worlds.

Application → Collector (Agent) → Collector (Gateway) → O11y Backend
Pattern 03

High Scale with Message Queue

Provides load-leveling by decoupling agents from consumers — smooths out traffic spikes and allows downstream consumers to process data at a steady rate.

Application → Collector (Agent) → Message Queue → Collector (Aggregator) → O11y Backend(s)

10 — Deep DiveUnderstanding Available Batching Mechanisms

The batch processor is like a ferry which has two rules for when it departs: it leaves when it's full, or it leaves after waiting a certain amount of time at the dock — even if it's not full. The batch processor operates on the exact same logic, controlled by 3 key parameters.

timeout
Controls maximum latency
The maximum latency introduced by the batch processor. A shorter time is good for near-realtime data needs. Default: 200ms. This is the "time at the dock" — the ferry leaves even if not full after this duration.
send_batch_size
Controls target batch size
The number of items (spans, log records, or metric data points) that will trigger the batch to be sent, regardless of timeout. Default: 8192 items. This is the "full ferry" trigger.
send_batch_max_size
The absolute safety ceiling
send_batch_size is a trigger, but it doesn't prevent a batch from growing larger. send_batch_max_size is the safety value — it ensures that no matter what, the batch sent to the next component is no larger than this value. If a batch exceeds it, it's split into smaller chunks. Essential when your backend has a strict request size limit. Default: 0 (disabled).
How it all works together

A batch is sent when either condition is met first

Timeout is reached OR the number of items in the buffer reaches send_batch_size. If send_batch_max_size is set, it acts as a final check before sending — splitting oversized batches into chunks that respect the limit.

Batch Processor Best Practices

✅
Place batch after sampling/filtering but before heavy processors
The batch processor should almost always be placed after sampling or filtering processors but before any processors that perform external lookups or heavy computations.
✅
Use a short timeout to avoid data taking too long to appear in backend
A timeout that's too high means your data will be stale in your backend before it even arrives. Tune based on your latency requirements.
✅
Set send_batch_max_size if exporter shows 4xx errors
If your exporter logs show 4xx errors indicating requests are too large, configure send_batch_max_size. All network-based exporters should have this set.
