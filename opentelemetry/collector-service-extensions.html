Service Block, Extensions
and Internal Telemetry

The service block is the runtime switchboard that activates your Collector. This guide covers all three sub-sections — extensions (health_check, pprof, zpages, file_storage), pipelines, and telemetry — plus how to make your export queue durable and how to observe the Collector itself.

Thejasekhar Reddy.G  ·  June 15, 2026

01 — The Service BlockThe Runtime Switchboard

The service: block is the runtime switchboard of your Collector. It's where you declare which components are actually active, how they connect into pipelines, and how the Collector reports on itself. Everything else in your config — receivers, processors, exporters, extensions — is just a definition. Without a reference in service:, none of it runs.

service: — the runtime switchboard that ties everything together

The service block has three sub-sections. extensions lists which long-running feature components are active. pipelines activates and orders the components for each signal. telemetry controls the Collector's internal logs and metrics — what it reports about its own health.

service: block — extensions, pipelines, and telemetry together
service:

  # 1. Which extensions to activate — must also be declared under extensions:
  extensions: [health_check, pprof, zpages, file_storage]

  # 2. Pipelines — only components listed here get activated at runtime
  pipelines:
    traces:
      receivers:   [otlp]
      processors:  [memory_limiter, batch]
      exporters:   [otlphttp]
    metrics:
      receivers:   [otlp]
      processors:  [memory_limiter, batch]
      exporters:   [otlphttp]
    logs:
      receivers:   [otlp]
      processors:  [memory_limiter, batch]
      exporters:   [otlphttp]

  # 3. Internal telemetry — what the Collector reports about itself
  telemetry:
    logs:
      level: "ERROR"    # INFO | WARN | ERROR — use ERROR in production
    metrics:
      level: normal     # none | basic | normal | detailed
The most important thing to understand

A component declared in receivers: or processors: does nothing unless it appears inside service.pipelines. The service block is what activates the Collector. Think of the rest of the config as ingredient definitions — the service block is the recipe that tells the Collector what to actually cook.

02 — ExtensionsLong-Running Features That Support the Runtime

Extensions are long-running features that support Collector runtime but do not process telemetry in pipelines. They run alongside your pipelines and serve three typical roles: health endpoints for Kubernetes, runtime profiling on the Collector itself, and durable local storage for queues.

Extensions — support collector runtime, do not process telemetry in pipelines
extensions: — health_check, pprof, zpages, file_storage
extensions:
  # Liveness and readiness probe for Kubernetes
  health_check:
    endpoint: 0.0.0.0:13133   # GET / returns 200 OK when healthy

  # Go profiler — CPU, heap, goroutines — for developers, not daily use
  pprof:
    endpoint: 0.0.0.0:1777

  # Built-in diagnostic web pages — no backend needed
  zpages:
    endpoint: 0.0.0.0:55679

  # Durable local storage — bind to sending_queue by name
  file_storage:
    directory: /var/lib/otelcol/file_storage
💚
health_check — endpoint: 0.0.0.0:13133
Exposes a simple HTTP endpoint that returns 200 OK when the Collector is healthy. This is what Kubernetes uses for liveness and readiness probes. Without it, K8s has no way to know if your Collector is actually working.
🔬
pprof — endpoint: 0.0.0.0:1777
The built-in Go profiler. It helps you analyze how receivers, processors, and extensions behave at runtime — CPU usage, heap allocations, goroutines, Mutex contention. Not for daily use. Enable it when you need to debug a performance issue, then disable it again.
📟
zpages — endpoint: 0.0.0.0:55679
Built-in diagnostic web pages with no backend needed — instant Collector visibility. The servicez page lists which extensions are currently available. The pipelinez page shows high-level Collector information and all assembled extensions. The tracez page provides live spans and their stats, and featurez provides live spans and latency samples.
💾
file_storage — directory: /var/lib/otelcol/file_storage
Durable local storage for export queues. When your backend is temporarily unavailable, the Collector writes queued data to disk instead of dropping it. Bind it to an exporter's sending_queue by name. Data survives Collector restarts.

03 — PersistenceSurviving Backend Outages with file_storage

By default, the Collector's sending queue lives in memory. If the Collector restarts while data is queued — or if your backend goes down for long enough to fill the queue — data gets dropped. The file_storage extension solves this. Bind it to an exporter's sending_queue by referencing it by name, and the queue becomes durable on disk.

Persistence with file_storage — exporter sending_queue survives restarts
exporters:
  otlphttp:
    endpoint: https://vendorname.example.com:4318
    retry_on_failure:
      enabled:          true
      max_elapsed_time: 10m
    sending_queue:
      queue_size: 50000
      storage:    file_storage   # binds the extension by name

# In service:
service:
  extensions: [file_storage]   # must be listed here to be active
retry_on_failure + sending_queue + file_storage

Three layers of resilience working together

retry_on_failure retries individual export attempts. sending_queue buffers data across retries so the Collector keeps accepting new data while retrying. file_storage persists that queue to disk so data survives a restart. All three together give you a production-grade exporter that doesn't lose data during transient backend failures.

04 — Internal TelemetryObserving the Collector Itself

The Collector exposes its own internal metrics — queue depth, dropped spans, received data, export errors. This is how you know if your Collector is healthy, falling behind, or dropping data. You configure this under service.telemetry.

Internal Metrics — pull (Prometheus scrapes) vs periodic (Collector pushes)

The metrics.level controls how detailed the internal metrics are. none disables them. basic gives you minimal metrics. normal is the standard production choice. detailed adds high-cardinality metrics useful for debugging. For logs.level in production, use ERROR to avoid flooding your log system with Collector noise.

Internal metrics — pull reader (Prometheus) and periodic reader (OTLP push)
service:
  telemetry:
    logs:
      level: "ERROR"
    metrics:
      level: normal
      readers:
        # Option A — Pull: Prometheus scrapes :8888/metrics
        - pull:
            exporter:
              prometheus:
                host: "0.0.0.0"
                port: 8888

        # Option B — Periodic: Collector pushes via OTLP
        - periodic:
            exporter:
              otlp:
                protocol: http/protobuf
                endpoint: https://telemetry.vendor.com:4318
metrics.address is deprecated in newer releases

In older Collector versions you configured internal metrics with metrics.address. That's deprecated. The current approach uses metrics.readers with either a pull reader (Prometheus scrapes it) or a periodic reader (Collector pushes via OTLP). Both can be configured simultaneously.
